# World generation — vanilla parity, and the 1024-chunk bench

Same machine (AMD Ryzen 7 5700G, 8c/16t), same grid: **32×32 = 1024 chunks**.
Folia: [`FOLIA.md`](FOLIA.md). C2ME: [`C2ME.md`](C2ME.md). Raw numbers: [`RESULTS.md`](RESULTS.md).

Cinder runs a **vanilla 26.2 Full pipeline** before it listens. Every stage is
ported from the decompiled 26.2 sources and verified block-by-block against
reference worlds generated by the real vanilla server.

## What each generator does

| | Cinder | Pumpkin | C2ME / Folia |
| --- | --- | --- | --- |
| Terrain | Vanilla 26.2 density-function graph + vanilla aquifer/ore-vein/`find_top_surface` semantics | Vanilla-like 3D noise routers | Vanilla Java |
| Biomes | Vanilla multi-noise parameter list (7594 points, dumped from `OverworldBiomeBuilder`) + `Climate.RTree` | Multi-noise | Vanilla Java |
| Surface | Vanilla `surface_rule` tree from `overworld.json` (`SurfaceSystem`) | Surface rules | Vanilla Java |
| Carvers | Vanilla `CaveWorldCarver`/`CanyonWorldCarver`, configs parsed from the embedded JSON, 17×17 source-chunk neighbourhood | Carvers | Vanilla Java |
| Features | Vanilla `FeatureSorter` + `PlacedFeature`/`ApplyBiomeDecoration` driving a port of the overworld's configured features (ores, trees, ground cover, springs, geodes, vegetation patches) | Feature engine | Vanilla Java |
| Column | Y −64..319, stone/deepslate/water/lava/ores | Full density + surface rules | Full |
| When | Server startup, then bind 25565 | On demand (this harness) | `forceload` after `Done` |

## Parity: measured against the real vanilla server

Reference: vanilla 26.2 dedicated server, seed 1, `generate-structures=false` and
every biome's `features` emptied (so the reference contains terrain, surface and
carvers only — the stages Cinder claims parity for). 48×48 chunks generated by the
server, `Status=minecraft:full` for all 2304, and byte-identical on repeat runs
(`bench/parity/gen_ref.py`; the server is tick-frozen so random ticks cannot drift
the output).

Cinder is dumped with `CINDER_SKIP_STAGES=features` (`--dump <dir>`) and compared
chunk-by-chunk against the region files with `bench/parity/diff.py`:

| Grid | Block agreement | Biome agreement |
| --- | ---: | ---: |
| 4×4 chunks | **100.000000 %** (1 572 864/1 572 864) | **100.000000 %** (24 576/24 576) |
| 8×8 chunks (16..23 × 8..15, carvers on) | **100.000000 %** (6 291 456/6 291 456) | **100.000000 %** (98 304/98 304) |
| 32×32 chunks = 1024 (bench grid) | **99.999506 %** (100 662 799/100 663 296) | **99.927966 %** (1 571 731/1 572 864) |

Over the full grid: median chunk agreement 100.000 %, 967 of 1024 chunks exactly
identical (57 chunks differ at all), worst chunk 99.8362 %. The residual 497 block
positions are

- 94 obsidian / 12 lava / 9 water / 95 water-vs-air: vanilla's **fluid
  post-processing** (it schedules fluid updates for carved positions, so lava
  meeting water becomes obsidian at generation time) — not implemented in Cinder;
- 278 sand/sandstone ↔ stone/dirt/grass positions in two chunks that are also
  biome-tie cells (below), i.e. the surface rule following a legitimately different
  but equally fit biome pick.

An earlier revision of this table showed ~6250 differences; they were the missing
`BiomeManager.getBiome` fuzzy lookup (vanilla's surface rules and carvers'
`topMaterial` do **not** use the plain quart-cell biome — they pick one of eight
corners of the 4-block cell around `pos - 2` by a fiddled distance seeded with
SHA-256 of the world seed). `src/vanilla_biome_manager.c` ports that, which fixed
the beach/desert surface edges.

Primitive-level checks against the same jar, all bit-identical
(`bench/parity/df_check.sh`, `bench/parity/noise_check.sh`):

- 20 density-function / noise-router targets (`sloped_cheese`, `offset`, `factor`,
  `jaggedness`, `final_density`, `preliminary_surface_level`, vein functions,
  climate functions, aquifer noise) over 200 aligned points each, compared as
  exact doubles.
- Biomes: 120 random quart-coordinate samples.
- Noise primitives (Xoroshiro128++, positional factories, perlin/normal/blended
  noise, legacy `java.util.Random`): 2784 printed values, bit-identical.
- Feature RNG: 42 (step, index) decoration/feature-seed streams
  (`bench/parity/RngProbe.java` against `bench/parity/rng_probe.c`), including the
  decoration seed, `nextInt(bound)`, `nextFloat` bits and `nextLong` — bit-identical.
  Cinder's feature RNG is a `WorldgenRandom` over an Xoroshiro source (which is what
  `applyBiomeDecoration` builds); routing it through the legacy LCG instead moved
  every ore and tree.
- Carvers: the carved block set of chunk (20,11) and of all 64 chunks in the 8×8
  verification area matches vanilla exactly (`bench/parity/carve_diff.py`,
  cinder-only = vanilla-only = 0), and the per-source-chunk start decisions /
  tunnel seeds match the real registry (`bench/parity/carver_trace.java`).

The 0.07 % biome disagreement is entirely **tie-breaking**:
`bench/parity/biome_ties.py` shows every sampled mismatching cell is an exact
fitness tie between the two chosen parameter points (e.g. `ocean` vs
`deep_ocean` at the shared continentalness boundary, fittest-set size 2). Vanilla
resolves ties with the RTree's thread-local "last result" candidate, Cinder with a
per-chunk one, so either choice is legitimate — vanilla's own pick there depends
on which chunk its worker thread generated before.

### Features and structures on

The same 8×8 verification area against a **canonical** vanilla 26.2 world (default
settings: features *and* structures on, `$HOME/dev/ref-canonical26.2`), with
Cinder's feature stage enabled:

| | Block agreement | Biome agreement |
| --- | ---: | ---: |
| 8×8 chunks (16..23 × 8..15) | **98.099534 %** (6 171 889/6 291 456) | **100.000000 %** (98 304/98 304) |

Median chunk agreement 99.008 %, worst chunk 90.203 %. Measured with
`bench/parity/structure_split.py`, which splits the 119 567 mismatching positions
by whether the vanilla chunk contains structure blocks at all (trial chambers are
the only overworld structure in this area):

| | Chunks | Mismatching positions |
| --- | ---: | ---: |
| vanilla chunk contains structure blocks | 19 | **79 550** (66 %) |
| vanilla chunk is structure-free | 45 | 40 017 (34 %) |

That split matters: structures are placed during the same FEATURES stage as the
features, so in vanilla the feature pass sees structure blocks. Cinder has no
structures, so a structure chunk differs twice - the structure's own blocks, and
every feature decision that looked at them.

Outside the structure chunks the residual is now dominated by one thing:

- **~16 200 leaf positions** (`oak_leaves` 8 201 one way, 7 983 the other). Trees
  are placed at vanilla's rate and the first tree of every feature lands exactly
  where vanilla puts it; the columns that still differ are the later trees, whose
  candidates are decided against a level that vanilla had already decorated
  further out (see the decoration-band note below);
- **~5 000 ore positions** and **~3 000 vein positions**: the ore features'
  geometry, scan bounds, draw order and `shouldSkipAirCheck` all match the jar
  (checked against the bytecode), so what is left is the same level effect.

Two bugs found by chasing this, both fixed and worth remembering:

- `feat_height` ignored its `hm` argument and answered every heightmap query from
  map 0 (`OCEAN_FLOOR_WG`, whose predicate counts leaves). The tree decorator's
  `MOTION_BLOCKING_NO_LEAVES` check therefore rejected placements vanilla accepts,
  which consumed fewer RNG draws and displaced every later tree in the feature.
  `bench/parity/hm_probe.c` compares each maintained heightmap against a
  from-scratch recomputation, which is what proved the maps themselves were fine
  and the *reader* was wrong.
- The batch halo was terrain-only. A chunk's decoration writes into its eight
  neighbours, so those neighbours' features must run as well; vanilla's forceload
  rect is inflated by 2 chunks at FULL status, so its decoration band reaches two
  chunks out. Cinder now decorates one ring by default (`FEAT_DECORATE_RINGS`,
  see `src/vanilla_feature_driver.c`) and keeps a second ring of terrain for the
  outermost windows to read. Decorating the second ring too matches vanilla's band
  exactly and is worth +0.004 % agreement for about 25 % more feature-stage time,
  so it is a compile-time knob rather than the default.

Before the feature stage was a real port the same comparison was 90.35 %.

### Remaining known gaps

1. **Structures** are not generated, and they are 66 % of the remaining
   disagreement (79 550 of 119 567 positions in the 8×8 area above). The scope is
   narrower than "structures" suggests: `bench/parity/structures_present.py` reads
   the reference chunks' `structures` tag and the whole area contains exactly one
   structure type, `minecraft:trial_chambers`, assembled from 229 `minecraft:jigsaw`
   pieces. Porting it means the jigsaw structure type (structure-set spacing and
   salt, pool aliases, piece selection, junction placement) plus NBT template
   loading with rotation and mirroring — a bounded subsystem, but not a small one.
2. **Fluid post-processing.** Vanilla re-schedules fluid updates for carved
   positions, which turns some lava/water contacts into obsidian/stone (94 obsidian
   blocks in the reference world). Cinder does not implement water/lava
   post-processing; this is ~215 of the 497 residual positions, the rest being the
   two biome-tie chunks above.
3. **Lighting** is Cinder's own and outside block parity: vanilla recomputes light
   when a chunk is loaded and never stores it in region files.

## The 1024-chunk comparison

Every row is the same box (Ryzen 7 5700G, 8c/16t), the same target (1024 chunks,
32×32) and the same question: *how long until 1024 chunks of block data exist?*
Cinder and Pumpkin generate in memory; Folia and C2ME write Anvil region files and
boot a JVM first, so they also appear on the "spawn → 1024 chunks" row, which is
the number a player actually waits for.

| | Cinder | Pumpkin | Folia 26.2-7 | C2ME 0.4.2-α.0.52 |
| --- | --- | --- | --- | --- |
| Runtime | native C (Bend) | native Rust | JVM Java 25 | JVM Java 25 + Fabric |
| What the 1024 chunks are | vanilla 26.2 Full stages, in memory | `generate_single_chunk(..., Full)`, in memory | `forceload` → chunks written to Anvil | `forceload` → chunks written to Anvil |
| Threads | 8 (16) | 8 (16) | 8 workers | 8 workers |
| **1024-chunk generation** | **19.90 s** (**16.12 s**) | **4.88 s** (4.84 s) | **11.9 s** | **8.62 s** |
| per chunk | 19.4 ms (15.7 ms) | 4.8 ms (4.7 ms) | 11.6 ms | 8.4 ms |
| vs Cinder 8t | 1× (0.81×) | 4.08× faster (3.15×) | 1.67× faster | 2.31× faster |
| **spawn → 1024 chunks** | **20.2 s** @ 8t, **15.1 s** @ 16t | ~5.2 s if you gen then boot | **23.3 s** | **21.6 s** |

Sources: Cinder and Pumpkin rows are from `scripts/world_bench.py` run back to back
in one session (`bench/PUMPKIN.md`, 3 repeats per thread count, medians shown;
Pumpkin's 16-thread row settled at 5.10 s median / 4.84 s best). Folia and C2ME are
the medians of the 3-cold-world runs in [`FOLIA.md`](FOLIA.md) and
[`C2ME.md`](C2ME.md) on the same box (`forceload` → 1024 chunks on disk), and the
`spawn → 1024 chunks` column for them is process spawn → 1024 chunks on disk.

Reading the table:

- **Pumpkin is the fast one.** At the thread count they share (8) it is 4.08×
  faster than Cinder (4.88 s vs 19.90 s, medians); at 16 threads, 3.15× (5.10 s vs
  16.12 s). Pumpkin scales to 16 threads and then flattens, which is what its own
  README reports.
- **Cinder still beats both Java servers on time-to-world**: 15.1 s @ 16t spawn →
  1024 chunks + a live listener, against C2ME 21.6 s and Folia 23.3 s, even though
  the Java numbers include a JVM boot and Anvil writes while Cinder does not.
- **Cinder's own scaling is healthy** (medians of 3 runs each):

| Threads | Median | Best | per chunk |
| ---: | ---: | ---: | ---: |
| 1 | 96.65 s* | 94.60 s* | 94.4 ms |
| 4 | 27.78 s* | 27.50 s* | 27.1 ms |
| 8 | 19.90 s | 19.23 s | 19.4 ms |
| 16 | **16.12 s** | 15.27 s | 15.7 ms |

  \* measured on the earlier build from the same session, before the tree
  fix and the decorated halo (which cost about 13 % at 8 threads); the 8- and
  16-thread rows are the current build. 6.0× from 1 to 16 threads on 8 cores,
  with turbo and SMT.

Where Cinder's 20.1 s @ 8 threads goes (`bench/parity/timing.sh 8`, same grid):

| Stage set | Wall | Delta |
| --- | ---: | ---: |
| terrain (biomes + density + aquifers + veins + heightmaps) | 3.13 s | 3.13 s |
| + surface rules | 14.47 s | **+11.34 s** |
| + carvers | 14.88 s | +0.41 s |
| + features (full vanilla port) | 20.07 s | +5.19 s |

The surface stage is the hot spot: it evaluates the real `surface_rule` tree per
block position down every column, which is the price of the 100 % parity row
above. The feature stage costs 5.2 s for the whole 1024-chunk grid (it also
decorates the 1-chunk ring, so it generates 34x34 chunks' worth of decoration
rather than 32x32): it parses the
placed-feature / biome / configured-feature JSON through a one-time embed cache
(a 657-entry linear scan plus a re-parse per lookup was its dominant cost), and it
decorates chunks in nine passes grouped by `(lx % 3, lz % 3)` — chunks in one pass
are ≥3 apart, so their 3×3 write windows are disjoint and the pass is safe to run
on all threads. Output is identical at 1, 4, 8 and 16 threads.

The previous, approximate pipeline measured 7.67 s @ 8t / 5.86 s @ 16t. That is
not comparable: it ran a compact feature generator, whereas these rows run the
vanilla `FeatureSorter`, the real biome feature lists and ports of the overworld's
configured features (trees alone are most of the remaining delta), plus the full
`surface_rule` tree and carvers over a 17×17 source-chunk neighbourhood.

The GPU row that would belong in this table does not exist: the pipeline is C and
has no `!` call, so there is no device path for it. What the GPU target can run is
the Bend-side heightmap microbench, on a different workload, so its row is marked
and kept out of the ratios:

| Config | Workload | Time | per chunk |
| --- | --- | ---: | ---: |
| Cinder 8 threads | heightmap microbench, 65 536 chunks | 113.6 s | 1.73 ms |
| Cinder GPU (`--gpu 4GB`) | heightmap microbench, 65 536 chunks | **59.2 s** | **0.90 ms** |

Same code, same checksum on both sides (1065330270), 1.92x faster on the device.
A microbench chunk is a 16x16 heightmap, not a 16x16x384 Full chunk, so those
per-chunk figures are not comparable with the rows above.

## Reproduce

```bash
# extract vanilla 26.2 JSON (needs the server jar once)
python3 scripts/extract_vanilla_worldgen.py

# build (bend + clang)
bash scripts/build.sh

# 1024-chunk generation bench
scripts/bench_cinder_worldgen.sh 4 8 16      # Cinder alone, per-stage timings
python3 scripts/world_bench.py               # Cinder vs Pumpkin, writes bench/PUMPKIN.md

# Stability pins (seed 1, 32x32): any worldgen edit must keep these checksums
bash scripts/check_worldgen_checksums.sh
#   all stages -> checksum=759576596, features skipped (parity path) -> 644477432

# run the server, then ping it
./cinder --threads 8
python3 scripts/ping.py 127.0.0.1 25565

# parity in one shot: primitives vs the jar, then block-by-block vs the
# features-off reference world (uses $HOME/cinder-verify for its dumps)
bash bench/parity/verify_all.sh

# features-on parity against the canonical world, and the per-stage split
python3 bench/parity/stages.py
python3 bench/parity/attribute.py       # which stage introduced a mismatch
python3 bench/parity/timing.sh 8        # wall clock per stage set

# feature-stage diagnostics: dump a chunk's feature placements and the RNG
bash bench/parity/cprobe.sh bench/parity/feature_debug.c
bash bench/parity/probe26.sh RngProbe 1 256 128   # vanilla side of the same RNG

# rebuild the vanilla reference worlds from scratch (boots the real server)
python3 bench/parity/gen_ref.py
python3 bench/parity/gen_ref_variants.py

# isolate a difference
python3 bench/parity/diag.py  --dump <dump.bin> --region-dir <region> --cx 20 --cz 11
python3 bench/parity/carve_diff.py --cx 20 --cz 11
python3 bench/parity/biome_ties.py --dump <dump.bin> --region-dir <region> --nx 32 --nz 32

# GPU: is the target buildable here, and can it run?
bash bench/parity/gpu_probe.sh   # toolchain + device attributes + both runs
bash bench/parity/gpu_run.sh src/gpu_bench.bend   # build + CPU/GPU on WSL2

# C-side hygiene
bash scripts/check_c.sh          # syntax-check every module
python3 bench/parity/check_rng_kind.py    # every feature RNG has a source kind
python3 bench/parity/check_survive_blocks.py  # would_survive names are placeable
bash scripts/sanitize_core.sh ubsan 16 16 1
```

## GPU

Bend 2.0.5 has a GPU target, and it is the parallel-call notation rather than a
separate backend: `!` on a call makes `bend -o <out>` emit a companion
`<out>.gpu` program, and `<out> --gpu 4GB` runs those calls on the device (Metal
on macOS, CUDA 12 at `/usr/local/cuda` on Linux). Building one needs clang 19+.

**There is no Windows target.** `main.ts` and `comp.ts` contain no `_WIN32`
branch at all, the launcher is a POSIX shell script, and the emitted runtime is
POSIX by construction (`#include <pthread.h>`, `<unistd.h>`, `<sys/mman.h>`,
`mmap`-based pools). Native Windows is not a matter of installing Bun, clang and
the CUDA toolkit; the generated C would not build. WSL is the Windows-side route.

Two things follow for Cinder:

- **The worldgen is not a GPU target.** Every stage is embedded C reached through
  one IO effect, and no Bend code in the pipeline uses `!`, so
  `./cinder-bench --gpu 4GB` has nothing to hand to the device and just runs the
  CPU pipeline - same checksum, same timing, flag ignored.
- **The heightmap microbench is.** `World.grid` is pure Bend fork-join, so
  `src/gpu_bench.bend` (`World.grid_gpu`) is the GPU entry point.

### Running it on this box (WSL2)

`bench/parity/gpu_probe.sh` diagnoses the whole chain, and shows the one real
obstacle: Bend's `gpu_probe` requires
`CU_DEVICE_ATTRIBUTE_CONCURRENT_MANAGED_ACCESS`, and WSL2 reports **0** even
though `cuMemAllocManaged` works there (verified with a standalone CUDA program:
host writes are visible to the kernel and back). The device is otherwise fine -
RTX 3090, driver 616.64, CUDA 12.6, `UNIFIED_ADDRESSING = 1`.

`bench/parity/gpu_run.sh` therefore emits the C, relaxes that single condition
(`(void)managed;` in `gpu_probe`), builds it with clang 19 and the CUDA stub path,
and runs both modes. That is a workaround for WSL2's driver, not a fix; on
bare-metal Linux or macOS the unpatched binary is what runs.

| Workload | CPU (8 threads) | GPU (`--gpu`) | |
| --- | ---: | ---: | --- |
| 32x32 chunks (`src/gpu_bench.bend`) | 19 ms | ~2.4 s | device fixed cost (context, corpus map, module load) dominates |
| 256x256 chunks (65536 chunks) | 113.6 s | **59.2 s** | **1.92x faster**, identical checksum |

Both sizes produce the same checksum on both sides (16647010 and 1065330270
respectively), so the device path is correct, not just fast.

Tooling: `bench/parity/gpu_probe.sh` (toolchain + device + both runs),
`install_clang19.sh` (clang 19 from the apt.llvm.org debs, unpacked with
`dpkg -x`, no root), `cc_cuda.sh` (a `$CC` wrapper adding the CUDA stub path so
`-lcuda` links under WSL), `gpu_run.sh` (emit C, relax the gate, build, run both),
`gpu_timings.sh` (repeat runs of an already-built binary).
